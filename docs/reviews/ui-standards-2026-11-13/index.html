OpenRoom UI standards review

13 November 2026 · 39 fresh screenshots, each visually inspected · Review only

Priority: strengthen field boundaries, clarify Mark reviewed, and simplify mobile editing. The current semantic request statuses, separate Reviewed / Undo controls and PDF selection indicators are worth keeping.

Standards comparison

  • Sampled muted text contrast was around 5.0–5.3:1; error text 4.77:1; Action needed 7.35:1 and Uploaded 8.83:1. These samples meet the 4.5:1 normal-text benchmark. WCAG text contrast.
  • No horizontal page overflow was measured in 26 investor captures, including the main home surfaces at 320, 390, 768 and 1440 px. This supports the sampled responsive layouts, not every possible reflow state. WCAG reflow.
  • Twenty-four keyboard focus stops in the sharing dialog remained visible at their centers. No obscured focus was observed in this sample. WCAG focus visibility.
  • WCAG is the accessibility benchmark. NN/g and GOV.UK supply design guidance; they are not blanket compliance requirements for OpenRoom.

Recommended changes

High priority · 1

Strengthen empty field boundaries

Observed: Unfocused input borders measured 1.30:1 on the home background and 1.39:1 on the white question form. Empty fields have little separation from their surroundings.

Change: Use a stronger input-border token with at least 3:1 contrast where the boundary identifies the control. Keep card separators softer; they do not all need the same contrast.

View screenshot · WCAG 1.4.11
High priority · 2

Make completion labels explicit

Observed: The compact Review action immediately marks a document reviewed. Its wording can be mistaken for opening a document to review it. The accessible label is clearer than the visible label.

Change: Show Mark reviewed, using a separate action row on narrow cards if necessary. Keep the document title as the open action and retain the separate Reviewed / Undo state.

View screenshot · GOV.UK action labels
High priority · 3

Give mobile editing a dedicated preview mode

Observed: The personal-welcome editor stacks input, explanatory copy and preview inside a scrolling dialog with a large fixed footer. The preview is difficult to compare with the text being edited.

Change: Use a full-height mobile sheet with Edit / Preview tabs, a compact persistent save bar and clear scroll padding. Keep one primary Save action.

View screenshot · NN/g visual hierarchy
Medium priority · 4

Bring the first document higher on phones

Observed: With the illustrative welcome at 320 × 740, the first document card starts near the bottom and is only partly visible. The repeated room title, attention row, welcome and spacing dominate the first viewport.

Change: Show a short welcome excerpt with Read full welcome, reduce repeated heading space and keep the first document plus its action fully visible in the tested fixture. Preserve access to the complete personal message.

View screenshot · NN/g visual hierarchy
Medium priority · 5

Standardize phone control sizes

Observed: Most investor actions are 44 px high, but the email input and document-question Send / Cancel buttons are 36 px. Dialog close controls are 32 × 32 px.

Change: Use a 44 px touch-comfort target for primary phone inputs and actions. This is a consistency improvement: 36 px and 32 px controls do not automatically fail the WCAG AA 24 px minimum.

View screenshot · WCAG target size
Medium priority · 6

Make attention counts look interactive

Observed: The home counts such as 1 request and 1 unread reply look close to ordinary text. Their click targets are already comfortable, but their appearance gives little indication that they navigate.

Change: Keep them compact and add a subtle chip background plus a directional icon or underline. Preserve the main next-document action as the strongest control.

View screenshot · NN/g recognition
Medium priority · 7

Make appearance previews match the real room

Observed: The appearance preview labels itself sample content, but shows the older document list without the current Start here and Requests navigation. It cannot accurately preview the full current layout.

Change: Reuse current viewer components with sample data. Include Start here, all three navigation destinations, and the relevant mobile layout. Keep the separate permission-aware investor preview.

View screenshot · NN/g recognition
Lower priority · 8

Clarify mobile document metadata

Observed: Folder rows show PDF · 1.1 and similar outline numbers. These are easy to read as version numbers, while file size is hidden on phones.

Change: Label outline position explicitly when needed and prioritize useful type/size or update information. Use a consistent secondary-text scale, with important instructions larger than passive metadata. This is a design recommendation, not a WCAG minimum-font-size rule.

Scope and evidence

The current production build ran locally with disposable SQLite, disk storage and illustrative documents. The review covered entry, home, search/folders, questions/conversations, requests/receipts, PDF reading/tools/completion and owner personalization editors. No application source was modified. No deployment was performed.

This is a targeted UI and accessibility review, not conformance certification. Native devices, other browser engines, text-spacing overrides and screen readers were not audited. Sampled text measurements exclude inactive controls and are not an exhaustive contrast audit.
