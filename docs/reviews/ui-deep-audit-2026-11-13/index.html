Recommended sequence

First repair reachability, document identification and entry. Then simplify task layouts and make editing/preview behavior more dependable. Keep the existing visual identity; a new palette or wholesale redesign would not address these findings.

F1 · Fix first

Keep long document questions inside the viewport

Observed
At 390 × 844, a roughly 1,440-character question expands the PDF question dialog to 1,327 px. Its top is −242 px and Send begins at y=966. Focusing Send and requesting scroll into view does not bring it onscreen. Title, close control and submission controls are outside the visible area.
Change
Use the bounded, scrollable dialog pattern already present in the general “Ask the team” composer. Bound the textarea, give the body one intentional scroll region, and keep the title and actions reachable.
Verify
At 320 px width and a 390 × 500 viewport, enter the full allowed 5,000 characters. Reach Close, Cancel and Send with touch and Tab; no control remains outside an unscrollable dialog. Preserve the draft when opening and closing context controls.
Why
Visible controls and focus; this is a reproduced task blocker, not a spacing preference.

F2 · Fix first

Show the part of a document title that distinguishes it

Observed
At 320 px, Q1, Q2 and Q3 financial statements all display the same truncated title. The title span is 40 px tall with 80 px of content. The quarter disappears in both folder rows and search results; even a “q2” query returns a card whose visible title omits Q2.
Change
Allow full titles in narrow document rows, or provide an explicit reveal that works on touch. Use a layout that gives the title more width; keep period/version context visible where it is already known. Do not rely on a hover title or infer metadata unreliably from filenames.
Verify
An investor can distinguish Q1/Q2/Q3 before opening a file at 320 px, with touch, keyboard and increased text spacing. The same rule applies to search results and reviewed-document lists.
Why
Recognition rather than recall: expose the information needed to choose correctly.

F3 · Fix first

Make sticky form actions cooperate with focus and errors

Observed
Tabbing through room appearance places “Choose logo” behind the save footer: only 4.34 px of its 44 px height remains uncovered. The label is hidden. Submitting an invalid colour shows a visible footer error, but leaves focus on Save while the invalid input sits at y=709, behind the footer and partly below the 740 px viewport.
Change
Reserve space for the footer and use scroll padding/margins or focus-aware scrolling. Put the colour error beside its field as well as in the summary, and focus or link directly to the invalid field. Keep the existing persistent save actions.
Verify
Every keyboard-focused control and its focus indicator are fully visible at 320 × 740. Invalid-colour submission reveals the input and message without manual hunting, and preserves all other draft values.
Why
W3C focus-obscuration guidance and GOV.UK error recovery. The logo control is partially visible, so this audit does not label that particular case a failure of the AA “entirely hidden” criterion.

Keep entry possible when a welcome is long

Observed
A valid welcome of roughly 3,000 characters puts the email field at y=2,658 on a 320 × 740 screen. The entry page renders the entire message above the form. Inside the room the same type of content already has a compact excerpt and disclosure.

F5 · Next

Let search and folder browsing become the main task

Observed
At 320 px the first pinned card begins at y=513. Search results still sit below the room title, requests chip and personal note; a folder view repeats the room introduction, folder heading and breadcrumb before its list. These elements are readable but impose repeated vertical work.
Change
Use a compact room context while a query or folder is active. Put search, result count and folder breadcrumb directly above documents. Keep the personal note accessible as a small disclosure and restore the welcome presentation when returning home.
Verify
Compare time and scroll distance to find the Q2 document in home search and folder browsing. No lost query, folder or scroll position on Back. Keep all existing requests and questions entry points discoverable.

Visual hierarchy and progressive disclosure. This is a design recommendation supported by the layout, not a measured user-performance result.

F6 · Next

Preserve unsaved personal-welcome drafts on accidental dismissal

Observed
Editing the link welcome, pressing Escape, waiting for the editor to close and reopening restores the old saved welcome. The unsaved text is lost. The existing conversation composer already communicates that its draft is saved in the tab.
Change
Keep the draft in memory or session storage until Save or explicit Discard. Alternatively, show a concise unsaved-changes choice for Escape, close and navigation. Keep explicit Cancel/Discard semantics clear.
Verify
Escape, close, switching preview and opening related group controls preserve the draft or ask before discarding it. Saved content and draft content remain distinguishable; one investor link never inherits another link’s draft.
Why
Recoverability and consistent draft behavior; reproduced loss of unsaved text, not loss of persisted data.

F7 · Next

Make device preview labels truthful

Observed
At a 320 px admin viewport, Desktop and Phone both produce a 254 px-wide preview. At desktop width the “Desktop” preview is still constrained to the form’s right column. The shared components improve appearance fidelity, but these controls do not simulate their named viewport widths.
Change
Use “Fit to panel” for the current adaptive view and expose explicit dimensions for actual device previews. If offering Desktop, render an isolated viewport at a real width and scale the canvas, or open a dedicated preview. Keep real-link “Preview as investor” distinct from sample content.
Verify
Show actual render dimensions. Desktop and Phone produce the same breakpoints as real investor views at those dimensions, even when the owner is editing on a phone. Avoid nested scrolling that hides the preview’s useful content.
Why
Accurate feedback and correspondence between a control’s label and its effect.

F8 · Next

Reduce PDF toolbar height while searching on short screens

Observed
At 390 × 500 the normal sticky reader toolbar occupies about 114 px. Search adds a third row, bringing it to roughly 174 px—about 35% of the viewport before document content. Controls remain present; the issue is the reduced reading area.
Change
Design an explicit compact reading/search mode. Combine related navigation, put less frequent zoom/page tools in the existing overflow surface, and let search replace a row instead of continually adding rows. Preserve an obvious search close action and page position.
Verify
On short viewports, search, next match, current page and exit search remain reachable while the document keeps most of the reading area. Check orientation, keyboard viewport changes and zoom on an actual phone before shipping.
Why
Reflow guidance and task-focused hierarchy. The measured toolbar height is not, by itself, a WCAG failure.

Bring mobile admin document work above setup summaries

Observed
At 390 × 844, the room document screen shows global warnings, room identity/navigation and a large six-item Start here summary. Document search only begins at the bottom of the first screen, and upload controls are farther down. Other admin pages also repeat the warning stack. The warnings reflect the actual disposable environment, not a fabricated fault.
Change
Place Search and Upload/New folder before the pinned summary, and collapse that summary to a count plus Manage action on phones. Consolidate persistent system status while keeping urgent disk warnings visible and actionable. Use distinct labels for the section selector and room-options menu.
Verify

Follow-up opportunities

Question-list triage

The admin question list shows the latest message without a clear conversation status or question subject. Use a concise original-question subject, unread/replied status and labelled last reply so a founder can scan what needs attention.

View evidence

Readable audit targets

Several audit rows say “update branding” with a target simply labelled “room”. Show the room name and, when useful, the changed setting so similar events are distinguishable without opening each target.

View evidence

Empty and completed states

The empty room retains a search box despite containing no documents, and says to explore shared documents. Hide or disable irrelevant search and give a context-specific explanation. After all pinned documents are reviewed, distinguish “Start here complete” from reviewing every document; offer the existing Questions/Requests routes as relevant next actions.

View evidence

Dark-theme readiness — conditional

Forcing the existing dark CSS class produces active navigation/welcome-link contrast of 2.53:1 with default green, 2.55:1 with blue and 3.03:1 with yellow against the dark card, below 4.5:1 for normal text. No current theme switch was found. Resolve theme-aware brand ink before exposing dark mode; do not treat these injected states as the default experience.

View evidence

What should stay

The green/neutral identity, restrained cards, explicit Mark reviewed actions and separate Undo controls provide a coherent base. Document type/size metadata, private-question copy, due dates, request status and the room’s existing navigation are useful. The completed reading list collapses successfully, and the general question composer uses a safer bounded layout than the PDF composer.

Sampled normal light-theme text remains readable: muted navigation was 5.34:1, active green navigation 7.10:1, and the sampled urgent warning 4.53:1 against its background. The 320 px text-spacing stress capture did not introduce horizontal page overflow. These are limited checks, not a blanket accessibility pass.

Validate the design with task outcomes

For the next implementation, use four concrete tasks: find the correct quarter without opening a wrong document; submit a long page question on a short screen; edit and recover a personal welcome; and verify a sharing link’s protection from a phone. Track successful completion, incorrect openings, lost text and avoidable scrolling. Then have a few representative investors perform these tasks without guidance. Screenshot checks alone cannot establish comprehension or task speed.

Research applied

These sources provide design principles and accessibility criteria. The specific recommendations above are an application of those principles to OpenRoom’s screenshots; they are not claims that the sources evaluated this app.

  • Progressive disclosure — Use secondary disclosure for introductions, setup summaries and infrequent reader controls.
  • Visual hierarchy — Give the current task visual priority; repeated chrome should not outrank documents or actions.
  • Recognition versus recall — Keep identifying titles and protection context visible at the point of selection.
  • Error summary — Pair visible error feedback with a direct route to the invalid field.
  • Focus not obscured — Check focus against sticky content; distinguish partial occlusion from the entirely-hidden AA threshold.
  • Reflow — Check narrow content and the reading area around document viewers.
  • Text spacing — Stress layout with 1.5 line height, 2em paragraph spacing, .12em letter and .16em word spacing.
  • Text contrast — Compare normal text with the 4.5:1 threshold in the actual foreground/background context.
